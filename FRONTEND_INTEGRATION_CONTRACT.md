# INE Price Tracker Frontend Integration Contract

Version: 2026-09-19

This document is the complete frontend handoff for the INE Product Price Tracker. It is based on:

- `INE_PRICE_TRACKER_BUILD_SPEC.md`
- `Software_Engineer_Intern_Assignment.pdf`
- The current Express backend source
- The current Supabase schema
- Live recon of `https://demo.inelabteamdev.com/`

## Important implementation status

The current backend implements only these frontend-facing routes:

- `GET /api/health`
- `GET /api/store/catalog`
- `GET /api/store/search`
- `POST /api/tracked`
- `POST /api/cron/scrape` (cron/admin route, not a browser route)

The remaining dashboard routes listed in this contract are required by the product specification but are not yet implemented in the current backend. The frontend builder should use the response contracts below, but should not assume those routes currently return data until the backend routes are added.

The frontend must never call Supabase directly. The Supabase service-role key belongs only on the backend.

---

## 1. Runtime configuration

Frontend environment variable:

```env
VITE_API_BASE=https://<render-service>.onrender.com
```

Local example:

```env
VITE_API_BASE=http://localhost:10000
```

Every API request should be built as:

```text
${VITE_API_BASE}${path}
```

All API responses are JSON unless an upstream failure returns an unexpected response. Use a shared API client that checks `response.ok`, parses JSON, and throws a typed error containing `status`, `code`, and `message`.

CORS is configured by the backend with `CORS_ORIGINS`. The deployed frontend origin must be added there.

## 2. Global conventions

### IDs

- `store_product_id`: product ID used by the demo store, currently numeric but transmit as a string.
- `tracked_product_id`: UUID generated by Supabase for the local tracked product.
- `run_id`: UUID for one scrape run.

### Time

The backend stores timestamps in UTC ISO-8601 format, for example:

```text
2026-09-19T12:30:00.000Z
```

Display all user-facing times in Asia/Kolkata:

```js
new Intl.DateTimeFormat('en-IN', {
  timeZone: 'Asia/Kolkata',
  dateStyle: 'medium',
  timeStyle: 'short',
}).format(new Date(timestamp));
```

### Scrape outcomes

Only these values are valid:

```text
success | retried | failed
```

Use unambiguous visual states:

- `success`: green
- `retried`: amber
- `failed`: red

Never display a failed scrape as a successful price point. Failed scrapes create log rows but do not create price-history rows.

### Scrape strategies

```text
browser | none
```

The current recon found that the store price requires a browser-attested session, encrypted price response, real hover behavior, and trusted click behavior.

### Error object

Current generic backend error shape:

```json
{
  "error": "internal_error",
  "message": "human-readable server error"
}
```

Expected frontend error handling:

```js
const message = body?.message || body?.error || `Request failed (${response.status})`;
```

The frontend should show a useful error state and retain the previous screen data when a refresh fails.

## 3. Implemented endpoint: health

### `GET /api/health`

Purpose: backend availability check and Render warm-up target.

Authentication: none.

Current response:

```json
{
  "ok": true,
  "databaseConfigured": false,
  "now": "2026-09-19T12:30:00.000Z"
}
```

Fields:

| Field | Type | Meaning |
|---|---|---|
| `ok` | boolean | Backend process is responding. |
| `databaseConfigured` | boolean | Both `SUPABASE_URL` and `SUPABASE_SERVICE_KEY` are configured. |
| `now` | string | Current backend time in UTC. |

Expected future dashboard response:

```json
{
  "ok": true,
  "databaseConfigured": true,
  "now": "2026-09-19T12:30:00.000Z",
  "uptimeSec": 8421,
  "lastRunAt": "2026-09-19T10:00:00.000Z",
  "lastRunCounts": {
    "total": 8,
    "success": 7,
    "retried": 1,
    "failed": 0
  },
  "overdue": false
}
```

Frontend behavior:

- Call on app load.
- Poll every 60 seconds.
- Show a red warning when `overdue === true`.
- If `databaseConfigured === false`, show an admin/configuration error rather than an empty dashboard.

Note: the current `/api/health` does not yet return `uptimeSec`, `lastRunAt`, `lastRunCounts`, or `overdue`.

## 5. Implemented endpoint: store search

### `GET /api/store/search?q={query}`

Purpose: partial-name search for the tracking modal.

Authentication: none.

Example:

```text
GET /api/store/search?q=cloudbook
```

Current response:

```json
{
  "items": [
    {
      "id": 733,
      "slug": "ironwood-convertible-x",
      "name": "Ironwood Convertible X",
      "brand": "Ironwood",
      "category": "Laptops",
      "sku": "IRO-10733",
      "description": "The Ironwood Convertible X..."
    }
  ]
}
```

Behavior:

- Empty or missing `q` returns `{ "items": [] }`.
- Search is case-insensitive partial matching on `name`.
- The current backend fetches catalogue pages and filters locally.
- Debounce frontend input by 300 ms.
- Do not request on every keystroke.
- Show loading, empty, and error states.

Important backend limitation:

The current search implementation uses a default page size of 20 and may inspect up to 50 pages. The store catalogue can reshuffle between paginated calls. A future backend implementation should cache/normalize the catalogue or use a stable server-side search endpoint if available.

## 6. Implemented endpoint: track a product

### `POST /api/tracked`

Purpose: add or update a product in the user's tracked list.

Authentication: none in the current backend. If authentication is added later, send the backend's required auth token here.

Request body currently accepted:

```json
{
  "store_product_id": "733",
  "name": "Ironwood Convertible X",
  "url": "https://demo.inelabteamdev.com/product/733",
  "category": "Laptops",
  "brand": "Ironwood",
  "description": "The Ironwood Convertible X..."
}
```

Required fields:

- `store_product_id`
- `name`

Success response: HTTP `201` with the complete `tracked_products` row.

Example:

```json
{
  "id": "f0e8409d-7e4d-4b3b-9ad4-123456789abc",
  "store_product_id": "733",
  "name": "Ironwood Convertible X",
  "url": "https://demo.inelabteamdev.com/product/733",
  "category": "Laptops",
  "brand": "Ironwood",
  "description": "The Ironwood Convertible X...",
  "is_active": true,
  "scrape_interval_min": 120,
  "next_due_at": "2026-09-19T12:30:00.000Z",
  "created_at": "2026-09-19T12:30:00.000Z",
  "last_scrape_at": null,
  "last_outcome": null,
  "last_price": null,
  "last_currency": null,
  "last_in_stock": null,
  "consecutive_failures": 0
}
```

Bad request response: HTTP `400`.

```json
{
  "error": "store_product_id and name are required"
}
```

Frontend behavior:

- Send the catalogue/search item data after the user presses Track.
- Disable the button while submitting.
- Treat an existing `store_product_id` as an upsert, not a duplicate error.
- After success, update the local tracked state and navigate or refresh the dashboard.
- The initial scrape is scheduled immediately because `next_due_at` defaults to the current time.

Recommended future request body:

```json
{
  "storeProductId": "733"
}
```

If the backend is changed to this smaller body, it should fetch authoritative metadata from the store itself. Until then, use the snake_case body shown above.

## 9. Required endpoint: price history

### `GET /api/tracked/:id/history?range=24h`

Status: required; not implemented currently.

Valid ranges:

```text
24h | 7d | 30d | all
```

Recommended response:

```json
{
  "productId": "f0e8409d-7e4d-4b3b-9ad4-123456789abc",
  "range": "24h",
  "items": [
    {
      "id": "history-row-uuid",
      "scraped_at": "2026-09-19T12:35:12.000Z",
      "price": 15070,
      "currency": "INR",
      "in_stock": true,
      "stock_status": "In Stock",
      "stock_qty": 4,
      "strategy": "browser",
      "extractor": "encrypted-response-v1",
      "confidence": "high",
      "run_id": "run-uuid"
    }
  ]
}
```

Rules:

- Every item is a validated successful scrape.
- Failed scrapes are absent from this endpoint.
- A gap means the scrape failed or did not run; do not interpolate a fake price.
- Sort ascending for chart rendering or document the sort order clearly. Recommended: ascending by `scraped_at`.
- Use a step-after chart because observations are discrete samples.
- Out-of-stock samples still have valid prices and must remain in history.

## 13. Required endpoint: manual product scrape

### `POST /api/tracked/:id/scrape`

Status: required; not implemented currently.

Purpose: request an immediate scrape for one tracked product.

Rate limit: one request per product per minute.

Recommended accepted response:

```json
{
  "accepted": true,
  "runId": "run-uuid",
  "productId": "f0e8409d-7e4d-4b3b-9ad4-123456789abc"
}
```

Recommended responses:

- `202`: scrape accepted and running in the background.
- `404`: tracked product does not exist.
- `409`: product scrape already running.
- `429`: manual scrape rate limit exceeded.

Frontend behavior:

- Disable the button while the request is being accepted.
- Show `Scrape requested` after `202`.
- Poll product detail/history/logs until a new log appears.
- Do not wait indefinitely for the HTTP request itself; the scrape can take much longer than the API response.

### `POST /api/cron/scrape`

Status: implemented, but this is not a normal frontend endpoint.

Authentication header:

```http

```

Do not expose `CRON_SECRET` in frontend code or browser requests.

Success response: HTTP `202`.

```json
{
  "runId": "run-uuid",
  "skipped": false
}
```

If another run owns the lock:

```json
{

}
```

Unauthorized response: HTTP `401`.

```json
{
  "error": "unauthorized"
}
```

The external cron service calls this endpoint. The frontend should not call it.

### Challenge

```http
GET /api/challenge
```

This is consumed by the store's browser client, not by the frontend. It returns challenge material including a salt, timestamp, difficulty, signature, and WASM payload.

### Session

```http
POST /api/session
```

This requires the store's browser attestation proof. Do not call it from the frontend.

### Encrypted price

```http
GET /api/products/:storeProductId/price
Authorization: Bearer <session-token>
```

The response contains an encrypted field. The backend browser scraper decrypts it using the session token. Never expose this implementation or token to the frontend.

The price is only considered valid when the backend has a validated tuple:

```text
price + currency + stock
```

If the reveal fails, the frontend receives no history row. It should show the failed scrape log instead.

## 19. Frontend API client examples

```ts
const API_BASE = import.meta.env.VITE_API_BASE;

export async function apiFetch<T>(path: string, options?: RequestInit): Promise<T> {
  const response = await fetch(`${API_BASE}${path}`, {
    ...options,
    headers: {
      Accept: 'application/json',
      'Content-Type': 'application/json',
      ...(options?.headers ?? {}),
    },
  });

  const body = await response.json().catch(() => null);
  if (!response.ok) {
    const error = new Error(body?.message || body?.error || `Request failed (${response.status})`);
    Object.assign(error, { status: response.status, code: body?.error });
    throw error;
  }
  return body as T;
}

export const getHealth = () => apiFetch<Health>('/api/health');
export const searchStore = (query: string) =>
  apiFetch<{ items: StoreProduct[] }>(`/api/store/search?q=${encodeURIComponent(query)}`);
export const trackProduct = (body: TrackProductRequest) =>
  apiFetch<TrackedProduct>('/api/tracked', {
    method: 'POST',
    body: JSON.stringify(body),
  });
export const getTracked = () => apiFetch<{ items: TrackedProduct[] }>('/api/tracked');
export const getHistory = (id: string, range: HistoryRange) =>
  apiFetch<HistoryResponse>(`/api/tracked/${id}/history?range=${range}`);
export const getLogs = (id: string, limit = 100) =>
  apiFetch<LogResponse>(`/api/tracked/${id}/logs?limit=${limit}`);
```

For the current implemented search/track API, use snake_case fields exactly as documented. Do not silently convert request bodies until the backend contract is updated.

## 21. Database truth rules the UI must respect

The backend schema enforces:

- `price_history.price` is required and greater than zero.
- `price_history.currency` is exactly three characters.
- `price_history.in_stock` is required.
- `price_history.stock_status` is required.
- `scrape_logs` stores every attempt outcome.
- A failed scrape may have `price_found: null`.
- A failed scrape must not create a `price_history` row.
- `tracked_products.last_price` may be null before the first successful scrape.
- Out-of-stock products can still have a valid price.

Frontend implications:

- Do not render `0` as a placeholder price.
- Do not render `null` as a real price.
- Do not copy `last_price` into a failed history point.
- Use explicit empty states and chart gaps.
- Render stock independently from price.
